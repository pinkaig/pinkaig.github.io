IV.Blog

How I approach data, analytics, and software engineering, and what my projects have taught me.

Data Science

The Maths Behind the Models: From Coursework to Data Science

My degree is in real-time interactive simulation, but much of the maths it teaches is the same maths data science runs on. Linear algebra underpins both 3D transforms and the matrix operations inside machine learning models. Probability and statistics are what turn a pile of numbers into a conclusion you can defend. Algorithm analysis is what tells you whether a pipeline will still run when the dataset is a hundred times bigger.

My Machine Learning coursework, together with Probability and Statistics, Data Structures and Programming Massively Parallel Processors, gave me both sides of the work: understanding how a model learns, and knowing how to make the computation behind it efficient. Earning the AI Singapore AI4I Literacy in AI certification reinforced the practical side, including how AI is applied in real organisations and where its limits are.

What I've learned is that good data work starts with the question, not the model: understand what the people asking actually need, check the data honestly, and pick the simplest method that answers it well.

Business Intelligence

Model the Data First: Lessons from the NYP Events Manager

When I built the NYP Mobile Events Manager, the most important decisions weren't in the interface. They were in the database. Before writing any screens, I designed the relational data model in MySQL: how users, events, hosts and registrations relate to each other, and which keys and constraints keep that data consistent.

That groundwork paid off everywhere. The Laravel/PHP REST APIs could serve and update data cleanly, the React.js front end could rely on what it received, and questions like "how many people registered for this event?" became simple queries instead of special cases. That is the heart of business intelligence: a well-structured data model that makes the right questions easy to answer.

The same habit carried into my work as a Systems Engineer at Sakura System Services, where building client web applications started with understanding the business need and the data behind it before turning to the technical solution.

Software Engineering

Measure, Then Optimise: Engineering Lessons from Pulse Protocol

On Pulse Protocol, I engineered the rendering systems for a custom C++/OpenGL engine built on an Entity Component System architecture. Performance mattered, and the biggest gains came from understanding where the cost actually was. Sprite batching and grouping draws by shader and texture cut down GPU state changes and draw calls far more than micro-optimising individual functions would have.

Just as important was building systems the rest of the team could rely on. Modular, reusable components meant gameplay code didn't need to know how rendering worked, and integrating graphics tools into an ImGui editor let designers and artists iterate without touching engine code. That work involved collaborating across engineering, design and art to ship a playable game.

I now bring the same approach to VectorSpace, a no-code 3D authoring platform built in React, TypeScript and Three.js for an industry client: clear architecture, careful debugging, and features shaped by what the user actually needs.
